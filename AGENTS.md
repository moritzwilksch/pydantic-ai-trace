# Agent guide

## Start here

- Treat `README.md` as the product contract and `pixi.toml` as the command source of truth.
- Read the relevant implementation and tests before changing behavior.
- Keep changes narrow: update the owning layer and its observable-behavior tests together.

## Code map

- `src/pydantic_ai_trace/`: the public `Trajectory` format (`trajectory.py`), strict loading (`load.py`), derived facts such as tool pairing, cost, and totals (`analysis.py`), the viewer contract `TracePayload` (`payload.py`), renderers (`text.py`, `compact.py`, `_html.py`), and the CLI, scanning, and Starlette API/SSE.
- `frontend/src/`: Preact viewer. It renders a `TracePayload`; `generated/payload.ts` holds its types, `runIndex.ts` joins the analysis to message positions, and `components/` renders it.
- `tests/`: Python tests and trace fixtures. Frontend tests live beside their source as `*.test.ts[x]`.
- `hatch_build.py`: package-build guard for the bundled frontend.

## Verify against Pydantic AI

- Treat `pydantic_ai.messages` as the authority for message types and wire shape. `frontend/src/generated/payload.ts` is generated from it through `TracePayload`; run `pixi run gen-types` after changing a Python model or the Pydantic AI version, and never edit the generated file. Do not infer a field or discriminator from memory.
- Inspect the relevant Python definitions in an isolated environment without adding a project dependency. `pydantic-ai-slim` is sufficient and avoids provider extras; pin the version that produced the trace when known (for example, replace the package spec with `pydantic-ai-slim==X.Y.Z`):

  ```bash
  pixi run uv run --with pydantic-ai-slim python -c 'import inspect; import pydantic_ai.messages as m; print(m.__file__); print(inspect.getsource(m.UserPromptPart)); print(inspect.getsource(m.TextContent))'
  ```

- When serialization details matter, generate a minimal real dump rather than hand-writing JSON, then compare it with the generated types, the owning renderer, and an observable-behavior test:

  ```bash
  pixi run uv run --with pydantic-ai-slim python -c 'from pydantic_ai.messages import ModelMessagesTypeAdapter, ModelRequest, UserPromptPart; trace = [ModelRequest(parts=[UserPromptPart(content=["hello"])])]; print(ModelMessagesTypeAdapter.dump_json(trace, indent=2).decode())'
  ```

- Use `ModelMessagesTypeAdapter.json_schema()` when a union or discriminator remains unclear. Loading is strict: Pydantic AI's own validation, including its handling of legacy fields, is the only compatibility layer. Test the canonical shape produced by Python.

## Invariants

- Treat trace contents and paths as untrusted input. Keep filesystem discovery and reads inside the configured root.
- Preserve message and part order. Pair tool results chronologically, within a run, in `analysis.py` only; the frontend reads pairing, cost, and totals from the payload and never recomputes them.
- Parse once: every path is `load_trajectory` → `build_payload` → a renderer. Render part kinds without a dedicated component through `FallbackPart`.
- Keep the functional core (`trajectory`, `load`, `analysis`, `payload`, selection) separate from filesystem, HTTP, browser, and DOM effects.
- `src/pydantic_ai_trace/static/index.html` is generated by `pixi run build-frontend`; change frontend sources instead.

## Completion gate

Run focused tests while iterating. Before handing off a code change, run:

```bash
pixi run lint
pixi run typecheck
pixi run test
pixi run check-types
```

Run `pixi run test-lowest` when dependencies or their floors change.

Run `pixi run build` when frontend, packaging, or release behavior changes. Work is complete when relevant behavior is covered, required commands pass, and `git status` contains only intentional changes.
